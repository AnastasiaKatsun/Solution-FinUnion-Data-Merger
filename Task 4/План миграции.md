## Этап 7. Cutover & Stabilization (Cutover и стабилизация)

Этот этап — финальный, но он опирается на результаты всех предыдущих. Parallel Run — ключевой подэтап, который снижает риск потери изменений и делает переключение безопасным.

### Подэтап 7.1. Тестовый cutover и подготовка Parallel Run (T‑7…T‑2)

| Поле | Содержание | Результат |
| --- | --- | --- |
| **Подэтап** | Тестовый cutover + подготовка Parallel Run |  |
| **Содержание** | Провести тестовый cutover: эмуляция сбоя, проверка фолбэка и RTO ≤ 4 ч; подготовить view dim_customer_parallel с объединением legacy и MDM по global_client_id (приоритет MDM); добавить поле source_system в витрину; настроить dbt‑тесты для сравнения legacy vs new (порог расхождений ≤ 0.5%); подготовить feature flag parallel_run_enabled для Naive UI; проверить, что state machine корректно обрабатывает статусы из нового источника. | Успешное учение фолбэка; view dim_customer_parallel готов; dbt‑тесты сравнения настроены; UI готов к режиму Parallel Run; правила state machine проверены. |

### Подэтап 7.2. Parallel Run (T‑1 … T+3)

| Поле | Содержание | Результат |
| --- | --- | --- |
| **Подэтап** | Parallel Run (параллельная работа) |  |
| **Содержание** | Запустить параллельную работу: legacy‑поток продолжает работать, новый поток (MDM → Airflow → DWH) пишет в dim_customer с source_system = 'new_mdm'; BI и Naive UI переключаются на dim_customer_parallel; каждый час Airflow запускает dbt‑сравнение legacy vs new; при расхождениях \> 0.5% — алерт и остановка новых потоков; фиксировать конфликты статусов в Kafka с тегом parallel_conflict. | Данные из двух источников стабильно сравниваются; доля расхождений ≤ 0.5%; конфликты статусов логируются; UI/BI работают без простоев; подтверждён приоритет MDM. |
