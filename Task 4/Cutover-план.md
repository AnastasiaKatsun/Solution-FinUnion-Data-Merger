## Cutover‑план: домен «Клиентские данные»

### Подготовка (T‑30…T‑7)

**Что делаем:**

* Проверяем готовность MDM: правила дедупликации, маппинг на global_client_id, справочник статусов клиентов.
* Проверяем DWH: витрина dim_customer (SCD Type 2: valid_from, valid_to, current_flag), индексы по global_client_id.
* Проверяем пайплайны Airflow: загрузка из CRM/Core → MDM → DWH; dbt‑тесты качества (дубли, NULL, диапазоны).
* Настраиваем mTLS между всеми компонентами (MDM ↔ DWH, Airflow ↔ DWH), проверяем RBAC и аудит.
* Делаем полные резервные копии: MDM (база + метаданные), DWH (схема + данные), Kafka (топики с событиями клиентов).
* Фиксируем владельцев данных и SLA в DataHub.
* Готовим инструкции для команд (DevOps, DBA, BI, Frontend) и чек‑листы.

**Результат:** все компоненты готовы; бэкапы валидны; тесты качества проходят; политики безопасности включены.


### Data Freeze (T‑5…T‑1)

**Что замораживаем:**

* Запрещаем ручные правки в CRM/Core по полям, критичным для дедупликации: ФИО, дата рождения, паспорт, телефон.
* Запрещаем массовые загрузки/импорты в CRM/Core без согласования.
* Все изменения проходят только через MDM (единый канал записи).
* В state machine: новые переходы статусов фиксируются, но не меняют ключевые атрибуты клиента (ФИО, паспорт).

**Длительность:** 5 дней (чтобы все потоки успели синхронизироваться).

**Контроль:** мониторинг логов и метрик изменений; алертинг при попытках правки замороженных полей.


### Финальная выгрузка (T‑1, EOD)

**Какие данные выгружаем:**

* Полный снимок клиентов из MDM: global_client_id, full_name, birth_date, passport, segment, consents, board_name, owner_workflow.
* Статусные справочники: dim_status (коды, описания, группы).
* Маппинги: old_client_id → global_client_id (для трассировки).

**Формат:** Parquet (Lakehouse) + CSV (резерв) с контрольной суммой (SHA‑256).

**Куда:**

* Основной: Lakehouse (MinIO + Delta) — неизменяемый архив.
* Резерв: защищённая папка SFTP с шифрованием и подписью.

**Результат:** финальный снимок зафиксирован, контрольные суммы сохранены, lineage в DataHub обновлён.


### Загрузка (T‑1 вечер / T‑0 утро)

**Как загружаем:**

1. Очистка staging‑таблиц в DWH.
2. Загрузка из Lakehouse/резерва в staging.
3. Применение SCD Type 2 логики: обновление valid_to для старых записей, вставка новых, установка current_flag = TRUE.
4. Запуск dbt‑тестов: уникальность по global_client_id, отсутствие NULL в ключевых полях, проверка диапазонов.
5. Перестроение индексов и статистики.

**Инструменты:** Airflow (оркестрация), psql/COPY (загрузка), dbt (трансформации и тесты).

**SLA:** загрузка и тесты ≤ 4 часа.

**Результат:** витрина dim_customer актуальна; dbt‑тесты пройдены; контрольные суммы совпадают.


### Сверка (T‑0, после загрузки)

**Контрольные суммы:**

* Сравнение SHA‑256 финального снимка и загруженных данных.
* Счётчики строк: общее количество, количество current_flag = TRUE, количество дублей (должно быть 0).

**Бизнес‑проверки:**

* Доля клиентов с заполненным паспортом ≥ 98%.
* Доля клиентов с валидной датой рождения (не в будущем) ≥ 99%.
* Проверка маппинга: процент клиентов с global_client_id ≥ 100%.
* Сравнение выборочных записей (100–500 клиентов) между MDM и DWH по ключевым полям.
* Проверка SCD: корректность valid_from/valid_to на тестовых кейсах (изменение паспорта, смена сегмента).

**Критерии успеха:**

* Расхождения по счётчикам ≤ 0.01%.
* Бизнес‑метрики в пределах порогов.
* dbt‑тесты прошли без ошибок.


### Переключение (T‑0 день)

**Как меняем маршруты потоков:**

* Включаем новые пайплайны в Airflow (приоритет над старыми).
* Отключаем старые ручные выгрузки и прямые запросы к CRM/Core для витрин.
* Обновляем конфиги BI и Naive UI (Vue) на новые источники: dim_customer в DWH вместо старых таблиц.
* В state machine: все сервисы начинают читать статусы и профили клиентов только из DWH/MDM.
* Включаем мониторинг и алертинг на новые потоки.

**Подтверждение:** скриншоты дашбордов BI, ответы API UI, логи Airflow.


### Фолбэк

**Сценарии и действия:**

* **Ошибка загрузки/тестов:** откатываем staging, запускаем повторную загрузку; если не помогает — переключаемся на резервную копию DWH.
* **Расхождения \> порога:** останавливаем переключение потоков; возвращаем старые источники для UI/BI; запускаем расследование по lineage в DataHub.
* **Сбой Kafka/MDM:** используем финальный снимок из Lakehouse как источник истины; включаем файловый обмен с шифрованием.
* **Проблемы UI:** в Naive UI показываем статус «данные временно недоступны» и дату последнего обновления; фильтры отключаются или работают по кэшу.

**RTO (время восстановления):** ≤ 4 часа; **RPO (потери данных):** ≤ 24 часа (за счёт финального снимка).

**Тестирование:** перед cutover проводится учение: эмуляция сбоя, проверка времени восстановления, фиксация результатов.


### Мониторинг (T+1…T+7)

**Метрики:**

* Доступность витрин: % успешных запросов, время отклика (p95, p99).
* Качество данных: доля записей с current_flag, доля дублей, доля NULL в ключевых полях.
* Потоки: lag Kafka (если есть события клиентов), количество ошибок в пайплайнах Airflow, повторные попытки.
* Бизнес‑метрики: доля клиентов с паспортом, доля валидных дат, процент маппинга на global_client_id.
* Безопасность: события RBAC, попытки доступа без mTLS, аудит изменений.

**Алертинг:** пороги и каналы (Slack/Telegram/почта) фиксируются в документации.

**Частота отчётов:** ежедневно первые 7 дней, далее еженедельно.
