## Технологическая дорожная карта

| Зона | Что включить | Причина |
| --- | --- | --- |
| **Adopt (основа)** | **MDM** (единая золотая запись клиента), **Airflow** (оркестрация пайплайнов), **DWH на PostgreSQL** (витрины для BI и UI), **DataHub** (каталог данных, lineage, владельцы) | Это фундамент, без которого нельзя двигаться дальше. MDM решает проблему дублей и даёт единый global_client_id—это критично для state machine и Naive UI (чтобы статусы и профили были однозначными). Airflow нужен, чтобы управлять последовательностью шагов (сначала MDM, потом DWH).<br/>DataHub закрывает требования по lineage и владельцам данных—это обязательно для регуляторики и расследований. |
| **Evaluate (оцениваем, пилотируем, выбираем лучший вариант)** | **Debezium** (CDC из Core Banking), **Kafka** (событийная шина), **Lakehouse** (MinIO + Delta/Iceberg для сырых данных), **dbt** (трансформации и тесты качества) | Эти технологии дают сильные преимущества, но требуют пилотирования. Debezium и Kafka позволяют забирать данные из Core без нагрузки на систему—это важно для state machine (фиксировать переходы как события). Lakehouse нужен, чтобы хранить неизменяемый журнал событий и историю для расследований. dbt—это «простой способ» делать качественные витрины: тесты, документация, lineage «из коробки». На этапе Evaluate можно запустить пилоты и выбрать, насколько это подходит команде. |
| **Trial (пробуем в ограниченном контуре, проверяем гипотезы)** | **Circuit breaker и retry-логика** (для отказоустойчивости интеграций), **канареечные релизы витрин**, **mTLS + RBAC** (на уровне потоков), **шифрование и подписи выгрузок** | Это зона для проверки гипотез по безопасности и отказоустойчивости. Circuit breaker защитит UI (Vue + Naive UI) от каскадных сбоев Core Banking. Канареечные релизы позволяют включать новые витрины для части пользователей и быстро откатываться, если что-то не так. mTLS и RBAC закрывают требования по защите интеграций (в том числе в Service Mesh). Шифрование выгрузок нужно для регуляторики. |
| **Hold (не трогаем, оставляем как есть до особого решения)** | **Ручные выгрузки (Excel/CSV), самописные скрипты без тестов, старые локальные базы (Access, неподдерживаемые MySQL), прямые запросы из BI в Core** | Эти подходы создают риски: ошибки в отчётах, дубли, небезопасные интеграции. Их нужно явно зафиксировать в плане как «Hold» и запланировать отключение в рамках cutover. |
| **Future (запланировано на будущее, не делаем сейчас)** | **ML/AI для скоринга и рекомендаций, потоковая аналитика в реальном времени (Flink/Spark Streaming), шардирование DWH, автоматическое исправление дублей на основе ML** | Это перспективные направления, но они усложняют архитектуру. Для текущего этапа (построить надёжный DWH, state machine, BI, UI) они не нужны. |
