## Поток 1: Клиент из CRM → MDM (дедупликация и обогащение)

* **Источник:** CRM FinUnion, CRM RetailBank
* **Приёмник:** MDM Customer Hub
* **Передаваемые сущности:** Клиент (ФИО, дата рождения, паспорт, контакты, внешние ID)
* **Тип действия с данными:** Create / Update / Deduplicate / Resolve identities
* **Режим обмена:** Асинхронный (Kafka) + запрос/ответ для критических операций (REST для синхронной проверки дублей)
* **Обоснование:** Нужно построить «золотую запись» клиента и выдать global_client_id. Без этого нельзя корректно связать счета, карты, кредиты и обращения между FU и RB. В state machine это критично: статусы обращений и задач должны быть привязаны к единому клиенту.

## Поток 2: Счёт и транзакция из Core → Integration Layer → DWH

* **Источник:** Core Banking FinUnion, Core Banking RetailBank (через CDC)
* **Приёмник:** Integration Layer → DWH
* **Передаваемые сущности:** Счёт (баланс, статус, валюта), Транзакция (сумма, дата, тип, счёт‑отправитель/счёт‑получатель)
* **Тип действия с данными:** Create / Update (CDC), Enrich (добавление global_client_id), Validate (целостность, контрольные суммы)
* **Режим обмена:** CDC (Debezium/аналог) → Kafka → микропакетная загрузка в DWH (Spark/Flink)
* **Обоснование:** Core—мастер по счетам и транзакциям. DWH нужен для отчётности, BI и регуляторики. Важно сохранять порядок и целостность: в state machine статусы счетов и транзакций должны быть непротиворечивы.

## Поток 3: Карта и её статусы из Card Processing → Integration Layer → DWH/CRM

* **Источник:** Card Processing FinUnion, Card Processing RetailBank
* **Приёмник:** Integration Layer → DWH, CRM (для отображения статусов)
* **Передаваемые сущности:** Карта (PAN‑токен, card_id, тип, срок), Статус карты (active/blocked/closed), события (выпуск, активация, блокировка)
* **Тип действия с данными:** Create / Update / Status change, Mask/Tokenize (PAN), Validate (справочник статусов)
* **Режим обмена:** Real‑time асинхронный (Kafka); статусы для UI—через API (синхронно)
* **Обоснование:** Карточная система—мастер статусов и правил. CRM и BI должны видеть актуальные статусы, но не менять их. Для антифрода и расследований важен порядок событий.

## Поток 4: Кредит и график платежей из Loan System → Integration Layer → DWH

* **Источник:** Loan System FinUnion, Loan System RetailBank
* **Приёмник:** Integration Layer → DWH
* **Передаваемые сущности:** Кредит (лимит, ставка, валюта), График платежей (даты, суммы, статусы), Статус кредита (approved/issued/default)
* **Тип действия с данными:** Create / Update / Status, Validate (непротиворечивость лимитов и ставок), Enrich (global_client_id)
* **Режим обмена:** Near real‑time асинхронный (Kafka), микропакеты в DWH
* **Обоснование:** Кредитная система—мастер условий и статусов. DWH нужен для резервов, просрочки и отчётности. Важно не допустить рассинхронизации лимитов и графиков между FU и RB.

## Поток 5: События жизненного цикла → Kafka → Event Log / Data Lakehouse

* **Источник:** Core, Cards, Loans, CRM (любая система, меняющая состояние)
* **Приёмник:** Kafka → Event Log (append‑only) / Data Lakehouse
* **Передаваемые сущности:** Событие (event_id, timestamp_utc, source, entity_type, entity_id, old_value, new_value, reason)
* **Тип действия с данными:** Append (публикация события), Validate (JSON Schema), Ensure idempotency (по event_id)
* **Режим обмена:** Real‑time асинхронный (Kafka)
* **Обоснование:** Неизменяемый журнал событий нужен для трассировки, расследований, восстановления состояния и аудита. Это основа для state machine: по событиям можно восстановить историю переходов.

## Поток 6: DWH → BI и DWH → Регуляторная отчётность (выгрузка)

* **Источник:** DWH
* **Приёмник:** BI, Система регуляторной отчётности
* **Передаваемые сущности:** Витрины (остатки, обороты, просрочка, SLA), Отчётные наборы (шаблонные структуры)
* **Тип действия с данными:** Read (BI), Extract (регуляторка), Aggregate (внутри DWH)
* **Режим обмена:** BI—синхронный API/JDBC (с кэшем); Регуляторка—batch (ежедневная выгрузка по расписанию, SFTP/API)
* **Обоснование:** BI нужен для оперативных дашбордов; регуляторка—для соблюдения сроков и требований ЦБ/ФНС. Агрегации и витрины строятся в DWH, чтобы не нагружать OLTP.

## Поток 7: Метаданные и справочники → DataHub (публикация и потребление)

* **Источник:** Core, CRM, Cards, Loans (владельцы справочников и метаданных)
* **Приёмник:** DataHub / Каталог данных
* **Передаваемые сущности:** Справочники (статусы, типы, валюты), Метаданные (описания полей, бизнес‑термины, lineage)
* **Тип действия с данными:** Publish (при изменении справочника), Read (потребление другими системами)
* **Режим обмена:** On‑change асинхронный (Kafka/Webhook) для справочников; Sync для чтения метаданных
* **Обоснование:** Единый источник справочников и глоссария нужен, чтобы все системы (включая UI на Naive UI) использовали одинаковые статусы и термины. Это критично для согласованности state machine и UI.
