## Пайплайн 1. Простой пайплайн для DWH на PostgreSQL (промежуточное состояние, 3 месяца)

| Поле | Значение |
| --- | --- |
| **Пайплайн** | Загрузка витрин клиентов и счетов в DWH (PostgreSQL) для BI и базовой регуляторики |
| **Источник** | CRM FinUnion/RetailBank, Core Banking FinUnion/RetailBank |
| **Приёмник** | DWH на PostgreSQL (витрины: dim_client, dim_account, fact_balance) |
| **Тип** | ELT (Extract → Load raw → Transform в DWH) |
| **Инструменты** | Airflow (оркестрация), psql/COPY (загрузка), dbt (трансформации и тесты качества) |
| **Логика шагов** | 1) Airflow запускает задачу; 2) Загрузка сырых данных в staging-таблицы; 3) dbt строит витрины и запускает тесты (дубли, NULL, диапазоны); 4) При ошибках—алерт, повторная попытка; при успехе—обновление флага is_loaded = true |
| **Частота** | Ежедневно (EOD), плюс микропакет 1 раз в 15 минут для статусов |
| **SLA** | Витрины для BI ≤ 1 ч после EOD; статусы ≤ 15 мин |
| **Безопасность** | mTLS для соединений; PII маскируется на источнике; доступ по RBAC |
| **Контроль качества** | Тесты dbt: уникальность по global_client_id, обязательность полей, проверка диапазонов, контрольные суммы |
| **Потребители** | BI (дашборды), базовая регуляторная отчётность, Naive UI (Vue) для отображения статусов и остатков |

## Пайплайн 2. CDC-поток транзакций и счетов из Core в Integration Layer и далее в Kafka + DWH

| Поле | Значение |
| --- | --- |
| **Пайплайн** | Репликация транзакций и изменений счетов из Core (CDC) |
| **Источник** | Core Banking FinUnion и RetailBank (PostgreSQL/Oracle) |
| **Приёмник** | Integration Layer → Kafka → DWH (витрина fact_transaction) |
| **Тип** | CDC (Change Data Capture) → Streaming → ELT |
| **Инструменты** | Debezium (CDC), Kafka, Flink/Spark (обработка), Airflow (контроль), dbt |
| **Логика шагов** | 1) Debezium читает WAL/redo logs Core; 2) События публикуются в Kafka; 3) Flink обогащает global_client_id из MDM, валидирует схему; 4) Микропакетная загрузка в DWH каждые 15 минут; 5) dbt строит агрегаты и запускает тесты качества |
| **Частота** | Real-time (публикация в Kafka), микропакет в DWH—каждые 15 минут |
| **SLA** | Публикация ≤ 1 сек; витрина ≤ 15 мин |
| **Безопасность** | mTLS между Debezium и Kafka; ACL топиков; маскирование PII на уровне Integration Layer |
| **Контроль качества** | Checksum, контроль ссылочной целостности (account_id, global_client_id), проверка диапазонов сумм, тесты dbt на расхождения с Core |
| **Потребители** | BI, антифрод (потоковые правила), риск-менеджмент, регуляторная отчётность |

## Пайплайн 3. Поток событий жизненного цикла в Data Lakehouse (сырые логи для расследований и ML)

| Поле | Значение |
| --- | --- |
| **Пайплайн** | Сбор и хранение событий жизненного цикла (state machine) в неизменяемом виде |
| **Источник** | Все операционные системы (Core, Cards, Loans, CRM) через Integration Layer |
| **Приёмник** | Kafka → Data Lakehouse (S3/MinIO, формат Parquet/Delta) |
| **Тип** | Event streaming → Append-only → Batch для ML |
| **Инструменты** | Kafka, Spark/Flink, Airflow (управление зависимостями), Hive/Trino (для аналитики) |
| **Логика шагов** | 1) Системы публикуют события в Kafka (строго по JSON Schema); 2) Spark пишет в Lakehouse с партиционированием по event_date; 3) Создаются таблицы Delta/Iceberg с историей версий; 4) Для ML и расследований—отдельные пайплайны пересчёта агрегатов |
| **Частота** | Real-time публикация; загрузка в Lakehouse—streaming или микропакеты |
| **SLA** | Публикация ≤ 1 сек; доступность истории—всегда |
| **Безопасность** | Шифрование в покое и транзите; ACL на уровне бакета и таблиц; запрет на редактирование (append-only) |
| **Контроль качества** | JSON Schema, обязательные поля (event_id, timestamp_utc, entity_id), идемпотентность по event_id, проверка контрольных сумм |
| **Потребители** | Расследования и аудит, восстановление истории state machine, ML‑модели, ретроспективный анализ |

## Пайплайн 4. Выгрузка для регуляторной отчётности из DWH

| Поле | Значение |
| --- | --- |
| **Пайплайн** | Формирование и выгрузка отчётных наборов для регулятора |
| **Источник** | DWH (агрегированные витрины) |
| **Приёмник** | SFTP/API регулятора, локальное хранилище для архива |
| **Тип** | Batch ETL |
| **Инструменты** | Airflow, Python (pandas/polars), утилиты SFTP, GPG/OpenSSL (подписи/шифрование) |
| **Логика шагов** | 1) Airflow запускает выгрузку после закрытия дня; 2) Данные агрегируются по шаблону регулятора; 3) Рассчитываются контрольные суммы; 4) Файлы подписываются и шифруются; 5) Передача по SFTP/API; 6) Логирование статуса и контрольных сумм |
| **Частота** | Daily (EOD) |
| **SLA** | До 08:00 следующего дня |
| **Безопасность** | mTLS/SSH для передачи; шифрование файлов; цифровые подписи; аудит передачи |
| **Контроль качества** | Валидация по XSD/шаблону; сверка контрольных итогов; проверка контрольных сумм до и после передачи |
| **Потребители** | Регулятор, внутренний аудит |

## Сценарий 1. Обработка истории карточных операций (после слияния банков)

| Поле | Значение |
| --- | --- |
| **Источник данных** | Архивные выгрузки из Core и Card Processing FinUnion и RetailBank (CSV/XML/паркет) |
| **Характер данных** | Исторические, транзакционные, частично полуструктурированные (старые форматы) |
| **Целевое хранилище** | Data Lakehouse (для хранения сырых архивов), затем DWH (очищенные витрины) |
| **Способ обработки** | Batch ETL (один раз при миграции), затем CDC для новых данных |
| **Логика обработки** | 1) Загрузка архивов в Lakehouse; 2) Нормализация форматов, маппинг старых ID на global_client_id через MDM; 3) Валидация и обогащение; 4) Загрузка в DWH в ретроспективные витрины; 5) Пересчёт агрегатов и контрольных сумм; 6) Проверка расхождений между старыми и новыми данными |
| **Потребители** | BI (исторические отчёты), риск‑менеджмент (анализ поведения), антифрод (обучение моделей), регуляторная отчётность (исторические периоды) |
| **Особенности** | Долгая первая загрузка; нужны дополнительные тесты качества; важно сохранить lineage (откуда пришли данные) |

## Сценарий 2. Обработка событий клиентских каналов (чат, колл‑центр, мобильное приложение)

| Поле | Значение |
| --- | --- |
| **Источник данных** | Логи мобильных приложений, чат‑платформ, колл‑центров, шлюзов API |
| **Характер данных** | Событийные, полуструктурированные (JSON), высокая кардинальность |
| **Целевое хранилище** | Data Lakehouse (сырые события), DWH (агрегации по SLA и NPS) |
| **Способ обработки** | Streaming (Kafka) для горячих данных + Batch для ретроспективных пересчётов |
| **Логика обработки** | 1) Сбор событий в Kafka по единой схеме; 2) Обогащение global_client_id и session_id; 3) Фильтрация дублей и нормализация; 4) Потоковые агрегаты (SLA обращений, NPS); 5) Хранение сырых событий в Lakehouse для расследований; 6) Загрузка агрегатов в DWH для BI |
| **Потребители** | Клиентская поддержка (SLA), маркетинг (путь клиента), риск‑менеджмент, расследования инцидентов, BI |
| **Особенности** | Высокая нагрузка; нужна идемпотентность; важно хранить сырые данные для расследований |
