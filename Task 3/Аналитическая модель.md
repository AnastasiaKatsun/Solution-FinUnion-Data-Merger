## Выбранная модель: «звезда»

| Тип таблицы | Пример | Назначение |
| --- | --- | --- |
| **Fact** | fact_transactions | Основные события: транзакции, суммы, статусы, остатки после операции |
| **Dimension** | dim_customer | «Золотая запись» клиента: global_client_id, ФИО, дата рождения, паспорт, владелец, доска (board) |
| **Dimension** | dim_account | Счёт: global_account_id, валюта, тип счёта, банк (FU/RB), дата открытия/закрытия |
| **Dimension** | dim_product | Продукт/тип карты/кредита: тип продукта, категория, линейка, владелец продукта |
| **Dimension** | dim_date | Календарь: дата, день/неделя/месяц/квартал/год, тип дня (рабочий/выходной), праздники |
| **Dimension** | dim_channel | Канал операции: мобильное приложение, интернет‑банк, ATM, POS, отделение, API |
| **Dimension** | dim_status | Справочник статусов: код статуса, описание, группа (активен/заблокирован/закрыт), владелец, допустимые переходы. |

## Почему «звезда» подходит для OLAP‑нагрузки

1. **Простые и быстрые запросы для BI.** В «звезде» факты соединяются с измерениями через один JOIN. Для дашбордов в BI (и тем более для Vue + Naive UI, где нужны быстрые агрегации) это критично: отчёты строятся быстро даже на больших объёмах.
2. **Легко поддерживать и документировать.** «Звезда» проще: меньше уровней вложенности, понятнее связи.
3. **Удобно для агрегаций и срезов.** Фильтры по клиенту, дате, каналу, статусу работают эффективно. Это закрывает типовые отчёты: «остатки по клиентам», «транзакции по каналам», «просрочка по статусам».
4. **Хорошо ложится на пайплайны и dbt.** В dbt «звезда» реализуется через staging → dim → fact. Тесты качества (дубли, NULL, диапазоны) пишутся прозрачно.
5. **Поддерживает SCD (Slowly Changing Dimensions).** Например, dim_customer можно сделать SCD Type 2 (с valid_from/valid_to), чтобы хранить историю изменений профиля клиента (например, смена паспорта или владельца).
6. **Совместимость с защитой и контролем качества.** В ТЗ легко зафиксировать: «все JOIN выполняются по суррогатным ключам; внешние ключи не обязательны в DWH; контроль целостности—на уровне пайплайна и тестов dbt».
7. **Связь с state machine и трассировкой.** Поле kafka_event_id в факте позволяет быстро перейти от строки в отчёте к событию в Kafka/Lakehouse. Это полезно для расследований: «откуда взялся этот статус/сумма».
